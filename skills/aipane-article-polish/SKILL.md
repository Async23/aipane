# 公开长文改写与定稿契约

目标读者是具备一定思考深度、但不具备特定行业或团队私有背景的公开网络读者。改写后的文章必须独立成篇、单主线推进、骨架硬核且零背景门槛好读。

## 1. 公开红线

- **全篇零源头残留**：正文中不得残留修改说明、平台导流痕迹，或任何指向“原稿 / 原视频 / 上一版 / 内部系统 / 上一轮推演 / 对话上下文”的字眼（除非文章主题本身就是研究 AI/LLM）；这一约束同样覆盖过渡段与收尾段。
- 若目标站点或发布渠道有既定渲染与元信息规范（如是否支持 Mermaid、导语块格式、分类枚举），优先遵循对应发布规范文档。

## 2. 完成态验收标准

成稿必须同时满足以下五项正交判据：

1. **彻底脱源与领域移植**
   - **外部素材**：剥离原材料的表层案例、标志性句式与原行文顺序，仅抽取底层问题张力或核心机制。
   - **内部复盘或冷门专有业务**：**严禁只做“删表名/改代号”的浅层字符串替换**（既容易被同行或同事反推来源，又逼外部读者先啃一套冷门业务规则）。执行**领域移植（Domain Transplantation）**——把底层架构冲突整体迁入开发者零背景门槛即可秒懂的公共场景（如云盘文件夹合并与文件哈希转码、电商购物车/订单与商品快照、代码分支与 CI 缓存、工单/群聊合并与附件解析）。
   - **验收标准**：刚看过原始素材的人或同组同事读完无法通过流程或举例反推来源；外部读者无需私有背景即可直入核心问题。
2. **骨架硬核、血肉具象**
   - 每条抽象机制、底层原则或跨学科类比，须配对公共领域的具象场景、具体主语和动作来承接；首次出现的抽象概念先用平实语言点破直觉，再落到专业名称，不以术语黑话填补抽离旧案例后的空白。
3. **单主线递进与理论内嵌**
   - 全篇沿一条核心问题链单向推进（痛点现场 → 病根拆解 → 解耦设计 → 适用边界），每节只往前推进一步，不把同一案例换套术语反复拆解。
   - 剔除不直接推动主线结论的支线科普；经典定理与一手文献在主线推导触及该机制时随用随引、点破即走，不在后半段另辟综述章节把前文道理重炒一遍。
4. **实证闭环与边界同口径**
   - 涉及具体操作系统、编译器、框架或工具的运行时行为断言（返回码、报错信息、签名校验、耗时量级、配置生效边界），须区分“当前环境实测（注明版本与现象）”与“规范/文档机制”，**严禁凭记忆将未经实测的细节写成确定性的数值或状态断言**。
   - 多方案对比或选型表格须交代各方案占优的前提条件，以及前提翻转后的切换去向，不打无条件的“最优解”标签；导语、摘要及小节首句的论断范围须与后文异常或例外章节同口径，前文直接带上前提条件。
5. **读者视角与自然节奏**
   - 保留降低阅读负荷所需的自然过渡、对比与节奏感，不把论述长文剪成干瘪速查条目；删去空泛拔高与对称排比口号，结尾收敛出可执行判断或适用边界。
   - 若文章孵化自长上下文推演或多篇旧文串联，定稿前可向用户建议手动调用 `/aipane-cold-critique` 对剥离元信息后的纯正文做一次零前情对抗冷审。
